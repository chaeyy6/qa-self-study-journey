# Managing Agile Project Artifacts

## Learning Objective

Understand how requirements and work items are organized and managed in an Agile project using Jira, and understand the tester's role in reviewing user stories, acceptance criteria, sprint planning, and story completion.

---

## Key Concepts

- Product Backlog
- User Stories
- Acceptance Criteria
- Gherkin / BDD
- Jira Epics
- Timeline Planning
- Sprint Planning
- Sub-tasks
- Sprint Board Workflow
- Definition of Done

---

## My Understanding

I learned how Agile requirements are organized and managed throughout the development process. The Product Backlog contains the prioritized requirements and other work items for the product, from which the team selects items for a Sprint.

I also learned that User Stories describe requirements from the user's perspective and are commonly written using the format:

**As a [type of user], I want [functionality], so that [benefit].**

Acceptance Criteria define the conditions that must be satisfied for a User Story to be accepted. They can be written using the **Given, When, Then** format, which helps make requirements more specific and testable.

Epics are used to group related User Stories that belong to a larger feature or functional area. During Sprint Planning, the team selects backlog items for the upcoming Sprint and establishes a Sprint Goal. Stories can then be broken down into smaller Sub-tasks and tracked through the team's workflow.

---

## QA Perspective

As a QA Engineer, reviewing requirements before testing is important because unclear or incomplete requirements can lead to ambiguity during test design and execution.

Testers should review User Stories and Acceptance Criteria to determine whether they are **clear, complete, unambiguous, and testable**. Testers may also contribute to refining acceptance criteria so that expected behavior can be verified effectively.

During a Sprint, QA activities are connected to the User Stories being developed. Testers may review requirements, create test cases, execute tests, report defects, and verify that the story satisfies the team's Definition of Done.

## Real-World Examples

- **Product Backlog:** Contains items such as Sign-Up, Login, Password Reset, and Location Services.
- **Epic:** User Account Management
  - Story: User Sign-Up
  - Story: User Login
  - Story: Password Reset
- **User Story:** As a user, I want to log in using my credentials so that I can access my account.
- **Acceptance Criteria:**
  - Given a registered user is on the login page
  - When the user enters valid credentials
  - Then the user should be successfully logged in
- **Sprint Workflow:**
  - To Do
  - In Progress
  - In Review
  - Done
- **Sub-tasks:** A User Story may be broken down into development, testing, or other supporting activities.

## Key Takeaways

- The Product Backlog contains prioritized requirements and other work items for the product.
- User Stories describe requirements from the user's perspective.
- Acceptance Criteria define the conditions that must be satisfied for a User Story to be accepted.
- Gherkin uses the **Given, When, Then** structure to express expected behavior in a clear and testable way.
- Epics group related User Stories under a larger feature or functional area.
- Sprint Planning determines which backlog items will be worked on during the upcoming Sprint.
- User Stories can be broken down into smaller Sub-tasks for different team members or activities.
- QA Engineers should review requirements and acceptance criteria for clarity, completeness, and testability.
- A User Story is considered Done when it satisfies the team's agreed-upon Definition of Done.
